# Technical Specification: Warehouse + Load Planning Platform

**Stack:** React + TypeScript (Vite) frontend • Node.js backend • Drizzle ORM • PostgreSQL • 3D visualization • Optimization + AI insights

This spec is written so a team can implement directly: folder boundaries, API contracts, DB schema (Drizzle + SQL), processing flows, and integration patterns.

---

## 1) Overview and Architecture

### 1.1 Product scope (from uploaded notes)

**Demo / v1 focus:**

* Single site initially: **San Diego** (warehouse mapped at pallet resolution). 
* Show both **current capacity visibility** and **system-recommended placement** for inbound material. 
* **Aging** based on “last received date,” with alerts (e.g., >3, >5, >7 years). 
* **Pallet constraint:** racks/areas support **≤ 2,000 lbs**. 
* Warehouse geometry available for four buildings (B-870/871/872/873). 
* CSV import acceptable initially (no live integration required for demo). 

**Network / phase 2:** load balancing across ~19 global sites is currently manual and needs a dashboard + recommendation engine.

## 3) Frontend–Backend–Database Data Flow

1. **User uploads CSV** (inventory export)
2. Backend stores raw file in object storage, creates `file_upload` row
3. Backend enqueues `IMPORT_INVENTORY(file_upload_id)` job
4. Worker parses, validates, upserts inventory + locations, writes `import_result` summary
5. Frontend polls or subscribes to SSE for completion
6. User selects inbound items (or “simulate inbound”), triggers **OptimizationRun**
7. Backend enqueues `RUN_PLACEMENT(optimization_run_id)`
8. Worker computes placements → writes `placement_plan`, `placement_plan_item`, and optionally `ai_insight`
9. Frontend renders:

   * heatmap capacity
   * placement recommendations
   * aging dashboards
   * 3D scene (warehouse + pallets)
10. PDF export request generates server-side PDF and returns URL

  role: text("role").notNull().default("user"), // user | admin | ops
  createdAt: timestamp("created_at").defaultNow().notNull(),

## 6.4 Example query + transaction patterns

### Upsert inventory from import (transactional)

```ts
import { db } from "@repo/db";
import { inventoryItems, locations } from "@repo/db/schema";
import { eq } from "drizzle-orm";

await db.transaction(async (tx) => {
  // ensure location exists
  const loc = await tx.query.locations.findFirst({
    where: (l, { and, eq }) => and(eq(l.siteId, siteId), eq(l.code, row.Location)),
  });

  const locationId = loc?.id ?? null;

  // insert inventory row (simple version)
  await tx.insert(inventoryItems).values({
    siteId,
    description: row.Description,
    qty: Number(row.Qty ?? 0),
    receiptDate: row.ReceiptDate ? new Date(row.ReceiptDate) : null,
    locationId,
    rawRow: row,
  });
});
```

### Capacity + aging summary

* Index on `(site_id, receipt_date)` and `(location_id)` (already included above).
* Compute:

  * utilized pallet positions = count(distinct location_id where items exist)
  * aging buckets = now - receipt_date

# 7) Database Layer (PostgreSQL)

## 7.1 Inventory import column mapping (from BATS inventory PDF)

The exported inventory dataset includes many fields such as **Storage Facility, Ship, Ship Class, Program Code, Requisition No, Qty, Description, CAGE, Manufacturer, Receipt Date, Location, Inventory Type, Condition Code, Remarks** and more. 
You should store:

* a normalized subset (typed columns)
* the full original row in `raw_row` (jsonb) for traceability

## 7.2 Indices and performance

* `inventory_item(site_id, receipt_date)` for aging dashboards
* `inventory_item(location_id)` for occupancy queries
* `location(site_id, code)` unique-ish (enforce if appropriate)
* `optimization_run(site_id, status)` for dashboards
* `ai_insight(target_type, target_id)` for fast retrieval

## 7.3 Example SQL (optional reference)

```sql
-- aging bucket counts
SELECT
  CASE
    WHEN receipt_date IS NULL THEN 'unknown'
    WHEN receipt_date < NOW() - INTERVAL '7 years' THEN '7y+'
    WHEN receipt_date < NOW() - INTERVAL '5 years' THEN '5-7y'
    WHEN receipt_date < NOW() - INTERVAL '3 years' THEN '3-5y'
    ELSE '<3y'
  END AS bucket,
  COUNT(*) AS item_rows
FROM inventory_item
WHERE site_id = $1
GROUP BY 1
ORDER BY 1;
```

# 8) AI and Optimization Logic

## 8.1 How algorithmic modules plug into backend

**Pattern:** “run registry” + “solver adapter”

* `optimization/registry.ts` maps `runType` → handler
* Each handler:

  * loads constraints + site snapshot (locations, inventory)
  * calls solver adapter
  * persists plan + metrics + insights

```ts
// apps/worker/src/handlers/runPlacement.ts
export async function runPlacement(runId: string) {
  const run = await loadRun(runId);
  const snapshot = await buildSiteSnapshot(run.siteId);
  const result = await placementSolver(snapshot, run.constraints);

  await persistPlacement(run, result);
  await generateInsightsForRun(run, result);
}
```

## 8.2 “Uploaded algorithm files” usage

You can accept uploaded algorithm packages (zip) and treat them as:

* **Data sources** (e.g., box catalogs, item dims)
* **Solver plugins** (custom heuristics)

Implementation:

* `POST /api/files/upload` with `kind="algo_zip"`
* Store in S3 + register in `file_upload`
* Worker unzips into a sandbox directory and validates manifest:

  * `manifest.json` (name, version, entrypoint, allowed deps)
* Run in a locked-down Docker sandbox (no network, CPU/mem limits)

## 8.3 Inference call integration flow (pseudocode)

```txt
Create OptimizationRun
  -> enqueue RUN_PLACEMENT(runId)

Worker RUN_PLACEMENT
  -> snapshot = query DB (locations, inventory, constraints)
  -> result = solver(snapshot)
  -> persist result (plan tables)
  -> insight = LLM("summarize constraints, hot spots, aging, reclaimed space")
  -> store AIInsight(target=runId, evidence={metrics, key_items})
```

## 8.4 Storing + retrieving AI insights

* Store insights in `ai_insight` keyed by `(targetType, targetId)`; retrieve via:

  * `GET /api/insights?targetType=run&targetId=:runId`
* For flights or cargo plans: `targetType="flight"` or `"plan"` (same table).

# 9) Integration and Workflow

## 9.1 Event flow: upload → process → render

**Upload inventory**

* UI uploads CSV
* Backend creates `import_run`
* Worker parses and reports:

  * rows processed
  * rows rejected + reasons
  * locations discovered (e.g., codes like `2069-B`, `3160-A`) 

**Run optimization**

* User confirms priorities (available space, proximity, weight limits) 
* Backend runs placement
* UI renders:

  * capacity heat map
  * “space reclaimed” metrics
  * recommended moves
  * aging heat map 

## 9.2 PDF export logic

* `POST /api/exports/pdf` with `{ runId, template: "run-report" }`
* Worker uses Playwright (recommended) to render an HTML report into PDF
* Store PDF in S3, return `exportId` + `url`
